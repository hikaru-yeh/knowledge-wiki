## Main Content

claude code
05/01/26
很多人寫 Claude.md 的方式，從一開始就走偏了。
以為塞進三百行人格指令、要求它當資深工程師、一步步思考，就能讓它乖乖聽話。
但事實上，Claude 仍然會猜錯建構指令，動不動就重寫整個檔案，甚至重複犯下你已經糾正過上百次的錯誤。
真正有效的 CLAUDE.md，從來就不是提示字的垃圾桶。
它應該是專案的最高權威、給資深工程師的技術簡報，精準控制在六十到八十行之內。
為什麼這麼短？
關鍵在於 Claude 的注意力是極度稀缺的資源。
系統提示本身已經佔用了大約五十條指令空間，你真正能有效利用的，頂多剩下約一百條。
一旦超過兩百行，後面寫的內容，效果就大打折扣。
**正確的 CLAUDE.md 結構，必須包含這五個部分：**
1. **關鍵指令 (Critical Commands)**：明確定義 build, test, lint 等指令該如何執行，避免 Claude 隨意猜測，浪費多輪對話。

2. **架構地圖 (Architecture Map)**：不必貼上完整的目錄樹，只需告知它檔案應放置的位置和關係。
3. **硬性規則 (Hard Rules)**：這是最核心的部分。每條規則都應回答：如果刪除這行，Claude 是否會因此犯錯？多使用大寫的 IMPORTANT、YOU MUST 強化語氣；負向規則（指出什麼不能做）比正向要求（指出該做什麼）有效十倍。
4. **工作流程偏好 (Workflow Preferences)**：明確指示 Claude 不要重寫整個檔案，也不要產生多餘的註解。
5. **避免重複內容 (Avoid Redundancy)**：不要寫 Claude 已經記住或可以自行推斷的資訊。它的項目記憶是有限的，重複只會稀釋其註意力。
這套方法，與其說是提示詞技巧，更像是 LLM 時代的「注意力經濟學」。
越聚焦、越具體、越明確「什麼不能做」，Claude 的輸出就越精準。

好的 CLAUDE.md，會隨著專案的複利效應不斷增長，初期省下溝通時間，長期則能自動規避所有歷史上的潛在問題。
它不是一個需要你不斷調教的助手，而是將你的技術品味與規範，固化成一個永不遺忘的資深合作夥伴。
各位，試著將你的 CLAUDE.md 砍到 80 行內，並用「這條規則是否能防止一個具體的錯誤」來審計，你會立刻看到效果。
